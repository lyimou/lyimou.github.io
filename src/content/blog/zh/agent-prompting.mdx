這個網站幾乎全部是我委派給編碼 Agent 完成的。真正有意思的不是程式碼，而是我套在 Agent 外面的那層工作協議 —— 以及這套協議在生效之前，具體是怎麼失敗的。

這篇是那套請求結構的整理，方便日後重複使用。

## 「幫我做個個人網站」的問題

那不是規格，是願望。Agent 會很樂意產出東西，而你沒有任何依據說它對不對。之後每一次修正都很貴，因為雙方沒有共同的「完成」定義。

更糟的是，**模糊的目標會讓 Agent 自己補空白**。有些猜測會猜對；猜錯的那些代價最高，因為你發現得太晚 —— 已經有三層工作疊在上面了。

所以下面這套協議的目的，是**把決策往前移**，移到還便宜的時候。

## 結構：六個階段，每階段都有批准關卡

請求被組織成明確的階段，並且明確要求 Agent 不得跳步：

1. **澄清與複述** —— 寫任何程式碼之前，先列出需求槽位、把模糊的風格詞量化、產出雙層複述（字面 + 深層意圖），並且最多問 3～5 個阻塞性問題。
2. **建立需求文件** —— 一份單一真實來源的文件，內含設計 token、資料結構、頁面清單與變更日誌。
3. **拆解與批准** —— 把工作切成有依賴關係的層級，停下來等批准。
4. **分階段執行** —— 一次一層。
5. **偵測偏離** —— 當現實與計畫衝突時，更新文件，而不只是改程式碼。
6. **合併與交付。**

這份清單裡最有價值的一條是**批准關卡**。它把一次長時間的無人監督，變成一連串短時間的有人監督。

## 技巧一：要求 Agent 複述目標，而且要兩層

在寫任何東西之前，我要求兩段文字：

- **字面複述**（你要求了什麼），以及
- **深層複述**（你真正想要的，加上你沒說出口的約束）。

價值在第二層。以這個專案為例，它挖出了「網站本身就是作品樣本，所以效能與無障礙是內容而不是裝飾」，以及「技術棧是既定約束，不是拿來討論的題目」。這兩點都不在我原本的訊息裡，但都改變了後續決策。

如果深層複述錯了，你只損失一則訊息。如果它缺席，你可能損失一週。

## 技巧二：把每個模糊的風格詞量化

「簡潔現代」無法執行。請求中要求把風格詞轉成具體的 token —— 顏色寫成十六進位值、字級寫成像素、間距用有名稱的基準單位、圓角與陰影都給明確數值。

回報出現在一個意想不到的地方：**一旦配色變成數值，它就可以被量測。** 我的 Agent 抓到：在白字壓在原本規劃的深色模式強調色上時，對比度只有 2.54:1 —— 低於 4.5:1 的無障礙門檻。你沒辦法稽核「清新的青色」，但你可以稽核 `#60A5FA`。

## 技巧三：強制一份寫下來的真實來源

第二階段產出一份需求文件，並附上一條規則：**文件優先於對話。**

這很重要，因為長時間的 Agent 工作階段會漂移。第 4 則訊息做的決定，到第 40 則時已經看不見了，而 Agent 會悄悄重新推導一次 —— 有時推導出不一樣的結果。寫下來的文件讓雙方都有東西可以指，也讓變更變得可見：每一個決定，要嘛已經在文件裡，要嘛就是一份修改提案。

我也要求文件把每個項目標成 已確認／待確認／假設／已廢棄。**「假設」是最危險的一類，而它們一旦被標記，就安全得多。**

## 技巧四：只接受可驗證的聲稱，而且由工具來驗

Agent 說「完成了」是聲稱，不是證據。規則是：**只要能用確定性方式檢查，就必須寫成腳本，而不是靠判斷。**

於是這個專案最後有五支小型驗證腳本，而不是一堆保證：

- **對比度稽核** —— 直接從 token 數值計算 WCAG 比值；
- **JavaScript 預算** —— 解壓建置產物，量測內聯腳本的位元組數；
- **視覺檢查工具** —— 在三種視窗寬度截圖每個頁面，偵測溢出與過小的觸控目標；
- **無障礙檢查工具** —— 驅動真實瀏覽器：鍵盤可達性、焦點可見性、標題層級順序，以及開關是否真的改變狀態；
- **連結稽核** —— 先對建置產物做，再對線上網域做。

關鍵後果是：Agent **不能說「版面沒問題」**。它必須跑一個有可能失敗的東西。

## 技巧五：分層要批准，而不是一次全批

一次批准整個專案，等於沒有審查。請求改成把工作切成層級 —— 骨架、設計系統、頁面、互動、內容、部署 —— 並且要求每一層之間都要明確批准。

來回次數變多，但值得。八層裡有兩層揭露了錯誤假設，而那些假設如果留到後面才發現會很貴。

## 技巧六：明確說出什麼東西絕對不准編造

最後一條是內容規則：**不得編造專案成果、數據、獎項或日期。** 任何關於我工作內容的文字，都必須能追溯到我自己提供的資訊，或倉庫裡的檔案。

這聽起來像道德提醒，其實是**正確性**提醒：一個編造出合理數據的 Agent，產出的東西比留下佔位符**更糟** —— 因為佔位符一看就知道還沒完成，而編造出來的數字看起來完成了，但它是假的。

## 四個錯誤，它們教我的比成功更多

我要求 Agent 記錄自己的失敗。以下四件都是這個專案裡真實發生的。

**一、它把沙箱錯誤報告成專案 bug。** 一次建置以某個結束碼失敗，第一個解釋是資源限制。真正的原因是一條 JavaScript 作用域規則：框架的 `getStaticPaths()` 執行在模組初始化作用域之外，因此讀不到頂層常數。教訓不是「Agent 錯了」，而是**Agent 會為失敗提供一個聽起來合理的敘事**。要索取原始錯誤與重現方式，而不是故事。

**二、一個編碼陷阱毀了檔案，而且被提交了。** 某個檔案經過一個會寫入 BOM、並且弄壞非 ASCII 文字的工具改寫，文件中的某個元件因此遺失，而損壞被烙進了第一次提交。兩件事修好了它：檔案看起來不對時去核對**原始來源**，以及加入一個能抓到它的檢查。

**三、它為一個不存在的 bug 宣布了修復。** Agent 的測試讀取 `window.game`。在傳統腳本裡宣告的頂層 `let` 建立的是全域**詞法**綁定，不是 window 屬性 —— 所以測試對一個一直正常載入的遊戲說「undefined」。接著 Agent 去「修」那個不存在的問題。這是四個裡最有啟發性的一個：**錯誤的探針會產出自信的錯誤結論**，解法是斷言在對象本身，而不是你以為等價的代理上。

**四、我的指示互相矛盾，Agent 必須選擇。** 我先說「不要發布任何課程程式碼」，後來又說「用課程內容填充網站」。這兩者不可能同時成立。有用的行為不是悄悄挑一個，而是**指出衝突、選擇保守的讀法（描述做過的事，不複製材料），並要求確認**。我希望它這樣做，所以必須留出空間：一個好的 Agent 應該被允許說「這兩條指示互相衝突」。

## 如果我要給剛開始的人幾句話

- **把問題前置。** 五分鐘的澄清，勝過五小時的重工。
- **讓 Agent 寫規格。** 如果它沒辦法用兩層複述你的目標，它就還沒理解。
- **把風格變成數字**，品味才能被測試。
- **要腳本，不要保證。** 每一個「已驗證」都應該說得出是哪個檢查產生的。
- **分片批准。** 自主性在任務層級很值錢，在專案層級很危險。
- **說清楚不准編造什麼。** 否則某個既合理又虛假的東西會進到你的作品集裡。
- **把失敗報告納入職責。** 上面四個錯誤會出現在這篇文章裡，是因為我要求了它們，而它們比成功案例更有用。

這套協議並不專屬於做網站。同樣的形狀 —— 澄清、寫下來、用工具驗證、分層批准、禁止編造 —— 幾乎適用於任何長時間的委派。
